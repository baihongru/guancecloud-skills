# 耗时 RCA 工作流

此工作流将最佳实践落成“固定前置查询 + 算法定位 + 模型理解 span 全属性后探索求证 + 可视化报告”。目标是提高前期效率，同时保留模型在后期分析复杂 span 属性时的灵活性。

## 总体原则

1. 前期不要让模型临场摸索查询方式，优先使用 `query-playbook.md` 中的固定查询剧本取数。
2. 算法只负责定位候选异常时间窗和判断数据是否适合继续自动下钻。
3. 趋势相似性算法负责把整体异常趋势和服务/资源趋势做排序，模型负责解释排序是否符合调用语义。
4. 模型在读取 `trace-field-guide.md` 后分析完整 span 属性，寻找慢环节和异常语义。
5. 跨域证据只在 trace/span 目标已经收敛后补充，选择规则见 `span-evidence-guide.md`。

## 阶段 1：基础查询与异常定位

使用 `query-playbook.md` 中的固定查询：

- Q1：查询整体耗时趋势。
- Q2：查询 span 数量、入口请求数量和 status 分布。
- 当用户提供观测云界面截图、光标时间、或明确说“一分钟/20 秒一个点”时，把界面粒度和光标时间当作优先证据。粗粒度只做概览，最终异常窗口必须用界面显示的细粒度或更细粒度复核。
- 对 30 分钟以内的短窗口，建议同时查询 `1m` 和 `20s`：`1m` 看趋势轮廓，`20s` 定位尖峰开始、结束和下钻窗口。

然后：

- 用 `normalize_owl_series.py` 归一化输出。
- 用 `series_windows.py stitch` 拼接分段结果。
- 用 `series_windows.py detect` 输出 `analysis_status` 和候选异常段。
- 用 `series_windows.py chart` 输出文本趋势图。

`analysis_status` 处理：

- `ok`：继续自动下钻。
- `no_anomaly`：报告无明确异常段，停止 RCA。
- `too_noisy`：异常点过多，停止自动下钻，请用户指定关注时间段。
- `too_sparse`：数据点过少或过稀疏，停止自动下钻，请用户缩小时间范围或补充上下文。

## 阶段 2：基础下钻

对每个可分析异常段执行：

- Q3：按 `service` 聚合 p99 趋势。
- 使用 `series_windows.py similarity` 对整体 p99 趋势和服务 p99 趋势打分，找候选服务。
- Q4：在候选服务中按 `span_type=entry` 和 `resource` 聚合 p99 趋势。
- 再次使用 `series_windows.py similarity` 对服务趋势和资源趋势打分，找候选接口。
- Q5：拉取代表性慢 span 样本，包括最慢样本、p99 附近样本、异常前基线样本和错误样本。

判断方式：

- 如果只有 `max/p99` 跟随异常，优先看尾部慢请求。
- 如果 `avg/p75/p90` 同时上涨，说明影响范围更广。
- 请求数和错误数只作为辅助信号，不替代耗时异常判断。
- 网关和 facade 服务默认后置，除非后续证据指向它们自身。
- 如果 1m 和 20s 给出不同异常窗口，以 20s 的可见尖峰作为下钻窗口；1m 的异常只能作为背景，不应直接决定慢 trace 采样范围。

## 阶段 3：模型理解 span 全属性

在分析慢 span 样本前，读取 `trace-field-guide.md`。

分析顺序：

1. 用 `trace_id`、`span_id`、`parent_id` 还原调用树。
2. 找 `duration` 最大、且能解释父级耗时的子 span。
3. 根据 `service`、`resource`、`operation`、`span_type` 判断慢点属于入口、内部逻辑还是下游依赖。
4. 根据 `status`、错误字段、超时和重试迹象判断是否存在显性异常。
5. 根据 `base_service`、`db_host`、`pod_name`、`env`、`version` 等字段判断影响范围和关联方向。

如果慢样本显示共同模式，执行 Q6 拉取完整 trace 子 span，并继续验证该模式是否重复出现。

## 阶段 4：异常语义与跨域求证

读取 `span-evidence-guide.md` 后，按异常语义选择求证路径：

- `status != ok`：查错误趋势、日志聚类、事件。
- Redis/DB/HTTP/RPC 变慢：查依赖实例影响范围、依赖指标、慢查询、连接数、服务端日志。
- 父子 span 耗时贡献异常：查同模式是否在多条慢 trace 中重复出现。
- 单 `pod_name`、host、`version` 集中：查基础设施、发布事件、版本对比。
- `local` span 变慢：查 profiling、应用日志、线程池或锁等待。

只有在 trace/span 证据和至少一个独立数据域或运维确认一致时，根因状态才写为“已确认”。

如果 `analysis_status=too_noisy` 或 `too_sparse`，报告只输出趋势图、异常段候选、停止原因和需要用户确认的问题，不继续自动下钻。
